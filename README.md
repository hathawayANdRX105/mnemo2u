# mnemo2u

Memory / RAG library for coding harnesses: graph relations + vector facts over a
three-store design.

```
turso   (truth: documents, chunks, caches, facts, reports)  ← commit point
redb    (graph: nodes, edges — adjacency index in memory)   ← derived, rebuildable
lancedb (vector: entity/chunk/fact ANN indexes)              ← derived, rebuildable
```

The truth layer is transactional; graph and vector indexes are derived from it
and can be rebuilt at any time. That split is what makes crash recovery and
index changes boring: write the truth last, rebuild the rest.

## Status

R1 — port of [nano-graphrag](https://github.com/gusye1234/nano-graphrag)
(`todo/01-nano-graphrag-port.md`) — implemented and exercised offline:

- chunking with token windows (`graph/chunk.rs`) — golden-parity fixtures
- entity/relation extraction with the gleaning loop (`graph/extract.rs`)
- merge with the reference's summary thresholds (`graph/merge.rs`)
- hierarchical community detection via `leiden-rs` (`graph/community.rs`)
- community reports (`graph/reports.rs`) — report markdown and CSV context
  byte-pinned against the reference (`crates/mnemo-core/tests/fixtures/report_golden.json`)
- query paths: local / global / naive (`query/`)
- insert & query facade with the reference commit order (`pipeline.rs`)
- LLM clients: OpenAI-compatible HTTP, cache with reference-parity args hash,
  deterministic mocks (`llm/`)
- stores: in-memory backends (tests), turso KV (truth), redb graph with an
  in-memory adjacency index, lancedb vector indexes
- commit protocol: truth-first writes plus a repair queue that replays failed
  derived writes on the next flush (`store/repair.rs`)
- durable end-to-end smoke: ingest → restart over the same files → drop the
  vector index → rebuild it from truth → identical retrieval (`tests/durable_e2e.rs`)

Report parity comes from running the reference Python, not from restating its
rules: `scripts/gen_report.py` drives `_community_report_json_to_str` and
`_pack_single_community_describe` from the local clone of
`nano-graphrag`, and every expected byte in `crates/mnemo-core/tests/fixtures/report_golden.json`
comes out of that run. The generator needs the venv described below, which is
not checked in — hence the committed fixture.

R2 — LightRAG-style write path (`todo/02-lightrag-upgrade.md`) — implemented
and audit-closed (PR #1–#3): incremental document-scope merge with no global
recompute, relationship vectors plus hl/ll dual-keyword retrieval, cascade
delete with rebuild, tracking rows, cost gates; five query modes with `mix`
defaults per the maintainer ruling.

R3 — hardened read path (`todo/03-retrieval.md`) — implemented and accepted
(PR #4/#5): scope pre-filter *inside* every arm (`ScopeKey::admits`), the
memory-layer fact store, the turso FTS lexical arm, the lancedb vector arm
with prefiltered ANN, the graph arm, optional temporal
re-ranking, RRF fusion with stable tie-breaks, and L0 delivery with
`degraded` arm reporting; AC1–AC5 ticked with measured baselines.

R4 — judgment capability (`todo/04-jev-integration.md`) — implemented
and merged (PR #7): a `JudgeClient` capability trait
(classify/compare/extract/rerank/find) behind a shared execution
envelope (`llm/envelope.rs`: retry on 408/409/429/5xx, deadline
timeout, sanitized provider errors, metering rows, egress gate) that
now also carries the chat path; backends are the jev-compatible
endpoint (first), `DisabledJudge` (default, zero calls until the
workspace opts in) and `JudgeMock` (fixtures + fault injection).
Write path: `index::judge::judge_write_candidates` as a pure function
(gateway wiring lands with the C01/C06 governance write gateway).
Read path: a judge arm after fusion — rerank (≤250 candidates,
all-near-zero treated as a miss) plus a find-style exists verdict;
failures mark `degraded: [judge]` and keep the fused order. Dedup
cache keyed `judge:{op}:{hash(model, request)}`; jev vocabulary
lives only in the backend's private wire layer.

Why the graph lives in redb rather than a dedicated graph engine or the turso
truth file: kuzu 0.11.3 — the only serious embedded property-graph engine —
cannot link next to `turso_core` (duplicate simsimd symbols, then an undefined
cxxbridge shim) and its upstream repository is archived, so it is out for good.
A separate redb file gives the graph its own lock instead of serialising
against the KV/fact writes on turso's single connection, and the adjacency
index is held in memory so multi-hop traversal is pointer chasing rather than
a SQL round-trip per hop. `todo/01-nano-graphrag-port.md` records the kuzu
evidence and the R2 re-entry condition that is now permanently closed.

Parity is checked against the reference implementation: fixtures under
`crates/mnemo-core/tests/fixtures/` are generated by scripts in `scripts/`
that run the reference Python code (see `todo/refs/nano-graphrag`, cloned
locally, not committed).

## Layout

The repo is a Cargo workspace. The root manifest is **virtual** — it lists the
members and the shared dependency versions, and carries no code of its own:

```
Cargo.toml              # virtual workspace manifest
crates/                 # the memory engine itself
  mnemo2u/              # the facade: the published surface of the library
  mnemo-core/           # the implementation, its tests and its examples
craft/                  # the task specializations
  narrative-core/       # the narrative kernel: story time and slot hashing
  novel-memory/         # the memory craft for a novel
  novel-review/         # the review craft: audit, statistics, consistency reports
  tavern-memory/        # the tavern craft
  coding-memory/        # the coding craft
bin/                     # the CLI entry points
  mnemo2u/              # the engine's operational CLI (package `mnemo2u-cli`)
  novel-review/         # the review craft's CLI (package `novel-review-cli`)
```

Three layers, one direction of dependency — **`bin/*` → `craft/*` → `crates/*`**:

- `crates/` is the **generic** memory engine: the bitemporal fact model, the
  three stores, the graph and vector indexes, the query paths, the evaluation
  harness. It knows nothing about fiction.
- `craft/` holds one **library** per *kind of work*: each bends that engine
  toward a craft. `novel-memory` scans a novel directory into fact slots and
  reads them back. `novel-review` audits the same novel against its rules and
  emits reports, statistics trees and a consistency index. `tavern-memory`
  keeps a character's canon and reports the events that contradict it.
  `coding-memory` remembers what a coding session did, the rules the project
  learned, and the procedures worth repeating. A craft carries no `main.rs`:
  wiring it to a command line is a `bin/` package's only job.
- `bin/` holds one package per **command**, each depending on the craft it
  drives. `bin/mnemo2u` serves the engine directly (it is the engine's own
  operational surface, not a specialization); `bin/novel-review` serves the
  review craft.

The two fiction crafts on the memory side share `narrative-core`: story-time
coordinates and the slot-key-plus-hash scheme. A tavern session is a story too,
and its canon is the same three layers, so the kernel is its own crate rather
than part of the novel one — they are two crafts on one kernel, not one on the
other. `novel-review` sits beside `novel-memory` without depending on it: it
reads the novel from disk; only its CLI carries the `memory` subcommand that
indexes the same corpus.

The rule that keeps the layers apart, stated once:

**A crate in `crates/` never depends on a crate in `craft/`, and a craft never
carries a `main.rs`.** The other directions are the whole point: the
specializations build on the engine, and the commands build on the crafts. A
craft that grew a binary would put the CLI's job inside the library, and the
day a second CLI wants the same craft it would either duplicate the wiring or
drag the first CLI's argument surface along.

One exception exists and it is deliberate: `bin/mnemo2u` depends on the facade
in `crates/` directly. The engine's operational CLI is the engine's own surface
rather than a specialization of it, and routing it through a craft would invent
a craft that does nothing but forward.

The facade re-exports `mnemo-core` under the module paths the library has
always published (`mnemo2u::core::traits::*`, `mnemo2u::store::*`, …), so
every downstream consumer keeps compiling unchanged. A path dependency must
point at a package, not at a virtual manifest, so a consumer of this repo
depends on the facade crate directly:

```toml
mnemo2u = { path = "../mnemo2u/crates/mnemo2u" }
```

A craft crate is depended on the same way:

```toml
novel-memory = { path = "../mnemo2u/craft/novel-memory" }
```

The implementation crate's integration tests exercise the library through the
facade (`mnemo2u::…`), not through `mnemo_core::…`: that published surface is
the contract, so the contract is what the tests pin. The dev-dependency that
makes this work closes a cycle (facade → core → facade), which Cargo allows
because the back edge is a dev-dependency only.

## Development

Requires a stable Rust toolchain. `lancedb` needs `protoc` at build time
(`apt install protobuf-compiler`, as CI does).

```bash
cargo fmt --all -- --check
cargo check --workspace --all-targets
cargo clippy --workspace --all-targets -- -D warnings
```

Tests run in CI (`.github/workflows/ci.yml`), including the golden-parity
suites; they need no network and no model downloads.

Regenerating the golden fixtures runs the **reference implementation** (Python),
so the expected values stay independent of the Rust port. The venv lives under
`crates/mnemo-core/tests/` because it is a test-only tool; it is gitignored and
never needed to build or run the suite:

```bash
python3 -m venv crates/mnemo-core/tests/.venvs
crates/mnemo-core/tests/.venvs/bin/pip install tiktoken

crates/mnemo-core/tests/.venvs/bin/python scripts/gen_chunks.py > crates/mnemo-core/tests/fixtures/chunk_golden.json
crates/mnemo-core/tests/.venvs/bin/python scripts/gen_extraction.py > crates/mnemo-core/tests/fixtures/extraction_golden.json
crates/mnemo-core/tests/.venvs/bin/python scripts/gen_hash.py > crates/mnemo-core/tests/fixtures/hash_golden.json
crates/mnemo-core/tests/.venvs/bin/python scripts/gen_merge.py > crates/mnemo-core/tests/fixtures/merge_golden.json
crates/mnemo-core/tests/.venvs/bin/python scripts/gen_report.py > crates/mnemo-core/tests/fixtures/report_golden.json
crates/mnemo-core/tests/.venvs/bin/python scripts/gen_prompts.py   # crates/mnemo-core/src/graph/prompts/*.txt
```

Only `gen_chunks.py` and `gen_report.py` need the venv: both measure their
expected output in tokens, so they must run against the real BPE (the report
context's budget splits between entity and relationship rows). The other four
are stdlib-only and run with any `python3`.
